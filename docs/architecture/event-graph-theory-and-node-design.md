# 事件图的叙事理论与节点关系设计分析

> 叙事理论与交互设计依据 · 2026-10-16。第 6.5 节标注当前前端实现与仍未打通的存储边界。<br>
> 研究问题：长篇小说的事件图究竟要连接什么？一个事件节点至少需要记录什么，才能指导后续章节写作？<br>
> 本轮交互约束：只保留一张事件图；卡片信息精简；点击节点后在右侧打开该节点的 Markdown 信息文档。<br>
> 与[事件图 AI 主线生成设计](./event-graph-long-novel-design.md)、[第一版执行步骤](./event-graph-v1-implementation.md)及[既有论文综合](./narrative-event-model.md)配套。本文聚焦事件的语义，不改变既有数据契约。

## 1. 结论先行

**事件图的核心不是把节点按顺序排好，而是让作者看见“为什么发生、谁推动它、发生后什么变了”。** 横坐标可以表示主线从左到右推进，底部括号表示阶段范围；这些是阅读与布局。故事能否成立，取决于另一层语义：事件之间的因果、前提、人物意图、信息揭示和伏笔兑现。

因此建议把同一张图理解成四个互不替代的层次：

| 层次 | 回答的问题 | StoryOS 中的载体 |
|---|---|---|
| 阶段与归属 | 这段故事正在解决什么，何时转向下一段？ | `arc` 节点及其子节点；底部括号是范围标识 |
| 两种顺序 | 事情何时发生？读者何时得知？ | `storyOrder`、`narrativeOrder`；顺序线可由它们派生 |
| 事件依赖 | A 为什么能导致 B？B 需要先有什么？ | `causes`、`requires` 等显式关系及说明 |
| 人物与信息状态 | 谁想达到什么？谁知道什么？结果改变了谁？ | 节点目标/结果、参与者前后状态、伏笔承诺；更细的认知状态留待后续设计 |

**产品建议（不是论文原句）：** 只保留当前这一张可拖动的事件图。作者创建事件时，默认只需回答「发生了什么」「为什么有人这样做/遇到什么阻力」「之后改变了什么」；AI 可据上下文补建议，作者确认后再形成正式主线。卡片只展示标题与变化，点击卡片就在右侧打开该节点的 Markdown 信息文档。不能为了模型结构把整套字段强制做成表单。

## 2. 论文给出的依据与边界

| 研究 | 可以支持的判断 | 对 StoryOS 的启发与边界 |
|---|---|---|
| [Trabasso 与 van den Broek，1985：叙事事件的因果表征](https://www.sciencedirect.com/science/article/pii/0749596X8590049X) | 事件是否位于因果链、具有多少因果连接，与读者的回忆、概括和重要性判断有关。 | 关键事件应能解释前因后果；“相邻”不等于“因果”。实验讨论的是故事理解，不能据此规定每个节点必须连几条边。 |
| [Chambers 与 Jurafsky，2008：叙事事件链](https://aclanthology.org/P08-1090/)及[2009：参与者叙事模式](https://aclanthology.org/P09-1068/) | 事件链是围绕共同参与者的部分有序事件集合；扩展模式把行动及参与者角色一起建模。 | 节点要有行动和参与者；长篇的多人物线不能简化为单一序列。论文从语料抽取常见模式，不等于小说应该服从统计上最常见的情节。 |
| [Riedl 与 Young，2010：兼顾情节和人物的叙事规划](https://ocs.aaai.org/Library/JAIR/Vol39/jair39-005.php) | 连贯情节需要因果上可成立的行动，以及能解释人物为何行动的目标与意图。 | 记录“前提—行动—结果”和人物目标；事件看似合理但人物没有理由去做，仍应提示作者检查。规划算法是研究实现，产品不必把小说变成硬性规划题。 |
| [Elson，2012：Story Intention Graphs](https://www.cs.columbia.edu/~delson/pubs/Modeling-Narrative-Discourse_Elson_R4.pdf) | 将文本、故事时间线与解释层区分；解释层表示命题、信念、目标、情绪及“促成、阻止、作为前提、尝试”等关系。 | 同一事件可以影响不同人物的目标或信念。StoryOS 应吸收分层思想，而不是照搬论文中的八种节点和十八种关系给作者填写。 |
| [TimeML 1.2.1 规范](https://timeml.github.io/timeMLdocs/TimeML_1.2.1a.html) | 时间的先后、重叠、包含等关系与事件本身可分开表示。 | 故事发生顺序与讲述顺序都不应冒充因果；倒叙和同时发生的支线需要保留双顺序。TimeML 是文本时间标注规范，不能直接当作小说编辑器界面。 |
| [Goyal 等，2010：Plot Units](https://aclanthology.org/D10-1008/)与[Lee 等，2021：人物叙事图](https://aclanthology.org/2021.naacl-main.391/) | 情节还包含人物受到的正负影响、心理状态、目标及其满足与否。 | “结果”不能只写物理事实，也要能追踪人物关系、知识或欲望的变化。两项研究的任务与数据规模不等于长篇小说产品已获验证。 |
| [Rashkin 等，2020：PlotMachines](https://aclanthology.org/2020.emnlp-main.349/)与[Tang 等，2022：NGEP](https://aclanthology.org/2022.aacl-short.24/) | 从概要写成连贯文本需要跟踪动态情节状态；图式事件规划可为生成提供可控中间结构。 | 事件图交给书籍工作区的应是当前事件及必要状态，而非整张图的原文堆叠。论文的实验效果不能保证 StoryOS 的某个提示词会自动写好长篇。 |
| [Sharma 等，2026：Kernel Events](https://aclanthology.org/2026.lrec-1.477/) | 关键事件与普通事件有别：删去关键事件会破坏叙事逻辑的连贯。 | 宏观图优先展示不可轻易删除的转折节点；细节留在章节。论文给的是检测研究，不能直接把“关键性”自动判为事实。 |

这些研究聚焦的对象不同：有的是读者理解实验，有的是文本标注或机器生成。因此下文的字段与交互是**基于论文和项目现状的设计推论**，不是某篇论文提供的统一标准。

## 3. 节点之间应有哪些关系

先区分**由位置或字段派生的关系**和**作者确认的语义关系**。把所有相邻卡片自动连成一条实线，会误导作者认为它们必然互为因果。

### 3.1 派生关系：不要求作者画边

| 关系 | 判定来源 | 画布表达 |
|---|---|---|
| 讲述上的下一事件 | `narrativeOrder` | 默认阅读引导线；只表示读者看到的次序 |
| 故事世界中的先后 | `storyOrder`，必要时补明确时间 | 在同一画布标出倒叙或预叙；具体时间在右侧文档中阅读 |
| 属于哪个阶段、场景 | `parentId` 层级 | 阶段括号、局部聚焦或场景范围，不画成因果箭头 |
| 属于哪一章 | `ChapterOutlineMapping` | 章节标记与写作交接，不决定事件是否因果相连 |

### 3.2 显式关系：每条边要能说清一句话

现有 `OutlineNodeRelation` 已支持五种类型。建议先固定含义，尤其区分前两种：

| 类型 | 建议语义 | 作者应能回答的检查句 | 示例 |
|---|---|---|---|
| `causes` 因果 | A 的结果实际促成 B 的发生或状态变化 | “因为 A 的哪个结果，B 才发生？” | 档案被烧毁 → 主角决定寻找唯一目击者 |
| `requires` 前置 | A 是 B 成立所必需的条件，但单有 A 不保证 B 发生 | “没有 A，B 还能成立吗？” | 拿到通行证 → 才能进入禁区 |
| `reveals` 揭示 | A 让人物或读者得知关于 B 的事实 | “A 揭示了什么？谁在此时知道？” | 对照笔迹 → 揭示早先那封信由同伴伪造 |
| `foreshadows` 伏笔 | A 埋下可在 B 被重新解释或兑现的线索 | “B 回看 A 时，多了什么意义？” | 提到失效门禁 → 后来成为脱身关键 |
| `contrasts` 对照 | 两事件在选择、关系或主题上形成对比 | “这组对照让读者看见什么变化？” | 前期为同伴撒谎 ↔ 后期公开同伴罪行 |

`causes` 与 `requires` 最先用于检查主线能否成立；`reveals` 与 `foreshadows` 用于控制信息何时到达读者；`contrasts` 服务主题表达，不能代替因果。已有 `NarrativePromise` 管理伏笔从铺设、触发到兑现的生命周期；`foreshadows` 可以是图上可见的事件连接，但长期承诺仍以承诺实体为准。

每条显式边至少保存 **源节点、目标节点、类型、简短依据**。依据应具体到“哪项结果/条件/信息”，例如“档案被烧使主角失去唯一的书面证据”，避免只写“推动剧情”。一个事件可以有多个前因、多个后果；支线可分叉、并行、汇合。画布布局坐标不参与关系判断。

### 3.3 阶段之间的关系

阶段是若干关键事件构成的**状态区间**，不是新的因果节点种类。底部括号回答“哪些事件属于同一段推进”，阶段从左到右默认表示宏观推进。真正让阶段 A 接到阶段 B 的，是 **A 的结尾事件改变了局面，使 B 有新的目标、阻力或前提**。

建议每个阶段概括四句话：**进入时的局面、这一阶段的目标/核心阻力、不可逆转折、离开时的局面**。跨阶段至少找得到一条由作者确认的关键事件因果或前置路径；没有时提示“过渡理由待补”，不要自动判定作品有错。当前 `arc` 节点已能存 `goal`、`conflict`、`outcome`，不必立即新增“阶段依赖表”。

## 4. 单个事件节点的信息结构

### 4.1 先确定粒度

宏观图的一张事件卡应代表**一次足以改变后续选择的行动、遭遇或揭示**。如果一句话只是“主角来到酒馆”而没有目标变化、障碍或新信息，它多半是场景细节；如果一句话包含数个独立选择及后果，就应拆成多个事件。关键转折可保留为父节点，再逐层展开近期要写的叶子事件。[Kernel Events 研究](https://aclanthology.org/2026.lrec-1.477/)支持区分关键与非关键事件，但“删除后是否破坏主线”在产品里应是启发式检查，而不是严格定义。

**叶子不是每个节点都要补的一层。** 没有子事件、已经足以指导章节写作的关键事件本身就是叶子；仅当一个事件横跨多章、包含数次独立选择或仍无法明确写作结果时再拆分。拆分后，关系应指向真正造成变化的子事件，避免父子节点重复承担同一条因果边。画布仍是一张图，按需在原图展开局部即可。

### 4.2 作者可见的最小结构

| 层级 | 字段或问题 | 作用 | 作者负担 |
|---|---|---|---|
| 卡片必显 | 标题；**这次之后什么变了** | 一眼判断此事件是否推动主线 | 标题必填；变化可先留待补充 |
| 右侧文档核心 | 谁想做什么；遇到什么阻力；产生什么结果 | 形成“意图—行动—结果”的可写事件 | 草稿可不完整；写作交接前补齐关键缺口 |
| 右侧文档延伸 | 关键参与者及各自前后状态；故事时间、地点；结构角色；揭示的信息 | 检查人物连续性、倒叙与场景合理性 | AI 建议，作者挑选和确认 |
| 独立对象 | 因果/前置等关系、叙事承诺、章节映射、正文覆盖证据 | 连接其他事件和书籍工作区 | 不混入一大段节点备注 |

“状态变化”建议至少允许写人物目标、人物关系、知识、资源/权力、外部局面中的一种；不要求每个节点把五种都填满。人物前后状态应按参与者分别记录：同一事件可能让主角获得线索，却让同伴失去信任。读者知情与人物知情也可能不同；当前契约没有独立的“谁知道什么”模型，第一版可在节点结果或关系依据中写清，等悬疑/倒叙使用需求明确后再结构化。

### 4.3 与现有契约的对应

| 设计含义 | 当前可复用字段 | 暂不新增的内容 |
|---|---|---|
| 事件身份与层级 | `OutlineNode.id/kind/parentId/title/summary` | 第二套图节点表 |
| 意图、障碍、结果 | `goal/conflict/outcome` | 固定“起承转合”表单 |
| 人物变化 | `OutlineNodeParticipant.role/stateBefore/stateAfter` | 未确认的全局人物心理状态机 |
| 时间与讲述 | `timeText/storyOrder/narrativeOrder` | 把画布 x 坐标当真实时间 |
| 场景与用途 | `locationText/structuralRole/narrativeFunction` | 每个草稿都必须标全 |
| 关系与承诺 | `OutlineNodeRelation`、`NarrativePromise` | 用“下一事件”线替代显式因果 |
| 写作状态 | `status`、章节映射、修订号 | 把 AI 候选视为已确认主线 |

这里的“变化可先留待补充”是**录入体验建议**；是否允许进入正式写作交接，仍按现有业务校验和已确认节点规则执行，不以界面默认值补齐缺失事实。

## 5. 一个最小示例

| 事件 | 人物意图与阻力 | 结果/变化 | 与其他事件的关系 |
|---|---|---|---|
| A：收到匿名信 | 主角想确认失踪者下落；信的来源不明 | 知道旧档案馆可能藏有线索 | A `causes` B：信中地址促使主角前往 |
| B：潜入档案馆 | 想取得原始记录；保安封锁 | 找到一页被撕毁的名单，同伴察觉主角已接近真相 | B `causes` C：同伴为掩盖名单而纵火 |
| C：同伴烧毁档案 | 同伴想掩盖自己涉案；主角试图阻止 | 书面证据消失，二人信任破裂 | C `causes` D：只能改向寻找人证 |
| D：寻找唯一目击者 | 主角需要重建证据；目击者拒绝配合 | 目击者承认见过失踪者，却暂时不愿作证 | D 是“争取证人”阶段的入口 |

示例中 A、B、C 可属于“追查档案”阶段，D 开启“争取证人”阶段。若小说先写 C，再倒叙 A 和 B，`narrativeOrder` 改变，故事中的因果关系仍是 A → B → C → D。若早先另有“同伴伪造匿名信”的事件，C 暗示了这件旧事，就可以用 `reveals` 指向那个旧事件；它不应被误画成 C 导致过去的伪造行为发生。

## 6. 固定交互：一张图，加一个 Markdown 节点文档

### 6.1 画布与右侧面板各承担什么

画布始终是同一张图，不增加“因果视图”“人物视图”“时间视图”等切换入口。**节点位置用于组织阅读，不定义关系。** 底部括号显示阶段；淡化的顺序线提示讲述路径。选中一个节点时，在原图上强调它的直接语义关系，右侧打开该节点的 Markdown 文档；点文档里的节点链接，画布定位到对应卡片，右侧换成那个节点的文档。这样读者始终知道自己处在同一部小说、同一张图中。

卡片默认只放：**标题、一句可观察的变化、阶段/章节或状态的简短标记**。关系类型、人物变化、具体动机、时间线例外与写作约束放进右侧文档。卡片不能因为作者在文档里写得更多就持续膨胀。阶段本身也可点击底部括号，在同一个右侧位置打开阶段文档；其重点是进入局面、目标与阻力、关键转折、离开局面以及通往下阶段的事件。

### 6.2 结构化事实与 Markdown 的关系

推荐将**结构化数据作为可计算的事实来源**，Markdown 作为这些事实的可读、可编辑呈现，再保留自由笔记。它不是第二份独立大纲。若同一条因果关系只写在任意一段 Markdown 中，图和书籍工作区就无法可靠追踪；若一切只存成字段表，作者又很难写出复杂的意图与解释。两者需要明确同步边界：

| 内容 | 权威存储 | 在 Markdown 文档中的样子 |
|---|---|---|
| 节点身份、类型、阶段归属、故事序与讲述序 | `OutlineNode` 的稳定 ID 与字段 | 标题下的简短元信息；阶段链接可点击 |
| 目标、阻力、结果及人物前后状态 | `OutlineNode`、`OutlineNodeParticipant` | 固定的“事件核心”“人物变化”段落 |
| 因果、前置、揭示、伏笔、对照 | `OutlineNodeRelation` 的源/目标 ID、类型、依据 | “关系”段落中的双向链接与解释 |
| 伏笔进度、章节映射、覆盖证据 | 对应的承诺、映射与正文记录 | 按需生成的引用和写作交接说明 |
| 作者的推演、未定问题、可替换写法 | Markdown 自由段落 | “作者笔记”等不参与自动校验的部分 |

右侧文档在读取时由 **节点 + 参与者 + 入边/出边 + 承诺 + 章节映射 + 作者笔记** 组装。这是一个详情聚合结果，不是新建一张“文档大纲”表。固定段落使用可解析的写法，自由段落保留作者的原文和格式；两者的保存规则应在编辑前清楚告知作者。

关系链接必须以**节点 ID**为目标，标题仅作显示名；重命名节点不应断链。若允许直接编辑 Markdown 的固定段落，保存时应先解析和校验，再把节点字段、人物、关系与笔记作为一次一致的业务变更提交；解析失败保留原文和错误位置，不悄悄丢失关系。AI 的建议也先以候选差异出现，作者确认后才进入文档及图中的正式关系。

### 6.3 一个事件文档的建议形态

下面展示作者看到的内容结构，`[[节点]]` 是可点击链接；存储层用稳定节点 ID 绑定，作者不必手输 ID。空信息显示“待定”即可，不用伪造内容。

```md
# 同伴烧毁档案

> 追查档案阶段 · 讲述第 3 个事件 · 第二章 · 已确认

主角找到名单后，同伴为掩盖自己涉案而烧毁剩余档案。

## 事件核心

- 目标：同伴想抹除名单；主角想保住证据。
- 阻力：双方都不能公开真实目的。
- 结果：书面证据消失，两人信任破裂。

## 人物变化

- 主角：相信同伴 → 怀疑同伴参与失踪案。
```

### 6.4 论文如何落进这一交互

| 理论关注点 | 在单张图上 | 在右侧 Markdown 文档中 |
|---|---|---|
| 因果链与关键事件：[Trabasso 与 van den Broek](https://www.sciencedirect.com/science/article/pii/0749596X8590049X)、[Kernel Events](https://aclanthology.org/2026.lrec-1.477/) | 选中时强调前因与后果；阶段转折占据主线位置 | 每条关键边说明“哪项变化促成下一事件”；可检查删除事件会失去什么 |
| 参与者与意图：[Chambers 与 Jurafsky](https://aclanthology.org/P09-1068/)、[Riedl 与 Young](https://ocs.aaai.org/Library/JAIR/Vol39/jair39-005.php) | 卡片不必塞满人物名 | “事件核心”“人物变化”说明谁想做什么、行动为何可信 |
| 信念、目标与解释：[Story Intention Graphs](https://www.cs.columbia.edu/~delson/pubs/Modeling-Narrative-Discourse_Elson_R4.pdf) | 揭示边与因果边视觉可区分 | 记录谁在此时得知、误信或隐瞒什么；复杂解释放在关系文字里 |
| 时间与叙述：[TimeML](https://timeml.github.io/timeMLdocs/TimeML_1.2.1a.html) | 仍保持一张图，用倒叙标记说明两种顺序不同 | 记录必要的时间、地点与读者此时获得的信息 |
| 长篇写作的状态跟踪：[PlotMachines](https://aclanthology.org/2020.emnlp-main.349/) | 画布提供当前阶段与关键事件的位置 | 当前章节只抽取相关节点、人物前后状态与必要关系交给书籍工作区 |

这些是产品映射，论文并未提出“右侧 Markdown 面板”这一界面方案。Markdown 的价值在于让作者能用连贯文字解释关系，同时让固定段落和链接仍可被程序识别。

### 6.5 与当前代码的差距

当前[单画布](../../src/renderer/features/event-graph/EventGraphSpine.tsx)已将阶段放在底部大括号，并在选中节点时强调语义关系；[右侧面板](../../src/renderer/features/event-graph/EventGraphMarkdownPanel.tsx)已渲染 Markdown 文档。前端还提供 [静态 JSON 示例](../../src/renderer/features/event-graph/data/staticStory.json)，用于检视结构和交互。正式快照仍从结构字段投影文档，不保存自由 Markdown 全文；关系编辑也尚未通过同一次正式业务变更持久化。

下一步应定下**固定段落解析、自由段落存储、稳定 ID 链接与原子保存**的完整契约，再开放 Markdown 全文编辑。现有 `notes` 可作为自由文本候选位置，但当前上限为 4000 字符；需要保存完整原文时应明确存储方式。解析器接受的关系词仍比正式契约更宽，需要收敛或正式扩展，不能让未经定义的类型悄悄进入主线。

## 7. 对当前事件图的具体建议与先后顺序

当前共享契约已有五种语义关系和参与者前后状态；[主线画布](../../src/renderer/features/event-graph/EventGraphSpine.tsx)目前主要绘制讲述顺序的连接，[写作上下文](../../src/main/story/application/outline/OutlineContextBuilder.ts)已消费部分因果与前置关系。这意味着**数据基础比当前画布表达更丰富**，眼下最值得补的是“边代表什么”和“节点到底改变了什么”的可见性；承载完整解释的地方固定为右侧 Markdown 文档。

1. **先明确线的语义。** 默认顺序线标作“讲述顺序”，选中节点时才强调已确认的因果/前置边；无显式关系时不把顺序线说成主线因果。
2. **优先展示事件变化。** 卡片保留标题和一句结果；点击后右侧 Markdown 文档展示目标、阻力、结果、人物前后状态与关系依据。草稿可轻量，交接到章节前再检查关键字段。
3. **让 AI 提议缺口而不是替作者填表。** 输入一句构思后，AI 在选中范围内提出少量事件及每条关键连接的依据；作者在候选预览中改写，再按现有流程整体确认。建议包括“从上一阶段如何转来、这个事件之后什么变了”。
4. **做三类轻量检查。** 提示没有可解释后果的关键节点、缺少人物动机的重大行动、跨阶段却没有过渡理由的主线；检查是建议，允许作者保留有意的悬念或跳接。
5. **最后再细化信息层。** 当真实长篇使用中经常遇到“人物此时知道什么”“同时发生的支线如何交汇”时，再引入结构化知识状态和更丰富的时间关系。不要先把整套学术标注体系放进界面。

书籍工作区接收的仍是**当前章节已确认叶子事件 + 必要前提、人物状态、结果约束 + 紧邻的下一事件**；作者在正文中自由写对白、动作和节奏。事件图负责守住“为何发生、发生后去哪”，正文负责“这一幕如何被读者体验”。

## 8. 待讨论的产品选择

- **关键事件标记**：是显式区分“主线锚点/局部事件”，还是先用结构角色与父子层级表达？建议先复用层级与 `structuralRole`，通过真实长篇样本验证是否需要独立字段。
- **跨阶段过渡**：是否要求每个相邻阶段有一条事件级因果/前置路径？建议先做提示，不阻止保存；悬疑故事可能故意延后说明。
- **知识状态**：是否需要人物和读者分别记录“知道/误信/未知”？建议先观察悬疑和多视角作品的痛点，再决定独立模型。
- **关系编辑负担**：关键节点手动确认边；AI 可建议边及依据，但不能把语义相似或时间相邻自动写为因果。

## 9. 本次调研的适用范围

上述文献为叙事理解、事件标注和自动生成提供理论与实验依据；没有一篇直接验证“StoryOS 的节点字段组合能提升长篇小说质量”。下一轮应找真实的长篇主线做任务测试：作者是否能凭图解释每一阶段的目标与转折、每个关键事件的前因后果，以及写章节时是否能从节点获得足够但不过量的指导。测试结果再决定字段和关系的正式规格。
