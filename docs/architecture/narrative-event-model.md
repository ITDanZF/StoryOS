# 叙事事件模型：论文综合与落地边界

> v0.1 · 2026-09-23 · 设计综合，不含实现  
> 目的：把 `docs/pdf` 里与叙事事件直接相关的论文收成一套可落地的事件模型，并标明它和现有目录、章节生成、检索工作流的边界。  
> 节点、关系、章节映射和叙事承诺的字段以 `docs/todo/outline-module-design-analysis.md` 第 6–9 节为准。本文解释这些字段从哪来、写作时怎么用，不另起一套表。

## 1. 结论

StoryOS 的叙事事件模型以 **STORYWRITER** 为主干。事件是可持久化的大纲节点，带时间、地点、人物、目标和事件间关系；高层事件先拆成子事件，再映射到章节；写某一章时只携带与当前事件相关的历史，生成和校验分成两步。

另外三篇补三条机制，不替换这根主干：

| 论文 | 补上的机制 | 落到现有设计 |
|---|---|---|
| DOC | 按叶子事件分段写，并给紧邻的下一个事件做过渡 | 章节生成的上下文包和覆盖检查 |
| GraphStory | 事件图是作者意图和正文之间可编辑的中间层 | 候选 diff、逐项接受、正文与事件的来源映射 |
| CFPG | 伏笔、触发、兑现是可查询的承诺，触发后才进入当前上下文 | `NarrativePromise` 及其状态 |

`docs/pdf` 里其余提到“事件”的材料各有一块可借用的判断，不进入这条主路径。EVOSPARK 的角色社会模拟、BiT-MCTS 的搜索引擎、成书论文的模型训练，以及 Agentic RAG 综述，都不定义 StoryOS 的事件实体。

产品上，目录继续回答“稿件放在哪里”，事件大纲回答“故事为什么这样发展”。二者通过章节映射关联。AI 可以提议事件、关系和承诺状态，提交前必须经过预览。

运行上，书籍对话是主 Agent，事件图和章节写作是它委派的子 Agent。写作子 Agent 启用前，主 Agent 先读取事件图已经确认的主线。没有主线时先问用户：确认则回去执行事件图子 Agent；用户明确放弃主线后，才启用写作子 Agent。

## 2. 已经成立的事实

这些行为以当前代码和已确认设计为准。事件模型接在外面，不改写它们。

- `get_book_outline` 返回书籍、分卷和章节，是目录快照。章节状态里的 `outline` 表示稿件生命周期，不是叙事事件。
- `generate_book_chapter_content` 内部写作调用 `maxTurns` 为 1，工具列表为空。写作器只收到一条不超过 4000 字的指令，并读取该章当前修订。找回其他章必须由外层完成，再写进这条指令。
- 带写入效果的请求继续不进入 `planned` 模式。写作图是显式代码路径。`src/main/agent` 不认识书籍、章节、大纲或事件。
- 小说向量索引的对象是尚未删除章节的当前修订纯文本。草稿和历史修订不入索引。人物、大纲、事件、伏笔尚未成为检索源；它们将来仍属于书库，确认后才可以作为 novel scope 的新来源。
- 后续业务边界已经把规划树和稿件目录分开：`outline_nodes`、`chapter_outline_nodes`、`outline_dependencies`、`story_events`、`narrative_promises`。本文不提前建这些表。

因此，事件模型要解决的是规划资产和写作主线。事件图子 Agent 把主线写入大纲。写作子 Agent 在启用前读取这份主线，不在生成过程内部自己检索整本书，也不把事件日志写进通用 Agent 引擎。

## 3. 论文如何分工

`docs/pdf` 中和叙事事件有关的材料，以及各自负责的问题：

| 材料 | 事件在文中的角色 | 对 StoryOS 的用法 |
|---|---|---|
| [STORYWRITER](../pdf/StoryWriter_中文精译版.md) | 事件元组组成大纲；子事件分配到章；按当前事件压缩历史 | 事件实体、章节映射、写作上下文的主干 |
| [DOC](../pdf/Improving_Long_Story_Coherence_With_Detailed_Outline_Control_中文翻译.md) | 层级大纲的叶子是具体事件，起草按叶子推进 | 一次写当前叶子，并控制对大纲的忠实度 |
| [GraphStory](../pdf/Collaborative%20Story%20Writing%20through%20Event-Based_中文翻译.md) | 块与事件构成可编辑图，AI 建议与作者原稿分开 | 人机协同的编辑与溯源，不做自由画布 |
| [CFPG](../pdf/Codified%20Foreshadowing-Payoff%20Text%20Generation_中文翻译.md) | 伏笔—触发—兑现三元组，以及待决承诺池 | 叙事承诺实体和“何时进入上下文” |
| [BiT-MCTS](../pdf/A%20Theme-based%20Bidirectional%20MCTS%20Approach%20to%20Chinese_中文翻译.md) | 高潮是锚点事件，前后事件分别承担上升与下降 | 节点的结构角色；搜索算法推迟 |
| [EVOSPARK](../pdf/Endogenous%20Interactive%20Agent%20Societies%20for_中文翻译.md) | 事件驱动反思，层级事件树是三种控制范式之一 | 事件前后的角色状态、角色是否在场 |
| [迈向人类水平的写书能力](../pdf/Towards%20Human-Level%20Book-Writing%20Capability_中文翻译.md) | 场景级规划脚手架，由粗到细再展开成书 | 短要点计划、叙事功能；不训练专用模型 |
| [Agentic RAG 综述](../pdf/10_Agentic_RAG_Survey_2025_中文翻译.md) | 不讨论叙事事件 | 检索质量先于更多智能体；事件确认后才成为检索源 |

消融和评估只说明“哪一块机制有用”，不说明 StoryOS 应该复现论文里的智能体数量或训练流程。

## 4. 主干：STORYWRITER

STORYWRITER 把长故事生成拆成三步：基于事件的大纲、把子事件编进章节、按当前事件压缩历史后再写正文。StoryOS 保留这三步的数据职责，并收成一个主 Agent 加多个子 Agent。主 Agent 是书籍对话。第一步的子 Agent 是事件图和章节写作。写作子 Agent 启用前，主 Agent 先读取事件图已经确认的主线。

### 4.1 事件是大纲，不是摘要句

论文的大纲智能体由 EventSeed 和 EventValidator 组成。EventSeed 按前提顺序产出事件，并为每个事件填写时间、地点、人物、目标和关系。EventValidator 检查该事件是否合理、是否接得上已有事件。附录里的事件要素就是：时间、地点、人物、目标。

这和“生成几句情节简介”不同。消融去掉基于事件的大纲后，六个评估维度一起下降，自动评估平均分从 4.3 降到 2.5，复杂性从 4.6 降到 1.1。对 StoryOS，这条证据支持把事件做成一等节点，而不是把大纲塞进书籍简介或章节标题。

落到已有字段：

- `Outline` 保存前提、主题、核心冲突、高潮摘要和结局意图。前提对应论文的 premise，高潮和结局可以为空，以便先探索再收束。
- `OutlineNode` 用 `kind` 区分故事弧、情节节点、场景和事件。时间、地点、目标、冲突、结果放在节点上。
- 人物放在 `OutlineNodeParticipant`，首版用名字和出场角色，并记录事件前状态与事件后变化。正式角色实体出现后再补可空的角色标识。
- 关系放在 `OutlineNodeRelation`：因果、前置、揭示、伏笔、对照。

校验写进事件图 Agent 的 Skill，并配确定性检查。确定性规则先做：无自环、因果与前置默认符合叙述顺序、参与者名字非空、叶子事件在映射前具备目标或冲突。语义检查由该 Agent 按需调用检查工具，结果是可失效的 `OutlineIssue`，节点一改就过期。不把 EventSeed 和 EventValidator 再拆成两个 Agent。

### 4.2 先拆子事件，再映射章节

规划阶段有两个模块。SubTasker 把高层事件拆成子事件。Weaver 决定每个子事件出现在哪一章。论文依据热奈特区分故事顺序和叙述顺序：倒叙和预叙可以改变读者看到的次序，因果和逻辑关系必须保住，读者才能把链条重建出来。

消融去掉这段非线性规划后，复杂性从 4.6 降到 3.8，其余维度下降较小。所以章节映射首先服务“这一章要完成哪些事件”，倒叙是同一套字段上的进阶用法，不是另一套大纲。

落到 StoryOS：

- `storyOrder` 是故事世界中的发生顺序，`narrativeOrder` 是读者看到的顺序。首版界面默认编辑叙述顺序，两者可以相同。
- 章节是容器。一个章节可映射多个叶子节点。一个节点首版最多映射一个章节；跨章事件拆成父节点和多个子事件。
- 删除章节只删除映射，大纲节点保留并变为未映射。删除大纲节点不删除章节正文。
- 目录 CRUD 与大纲 CRUD 分开。Agent 不能用 `create_book_chapter` 假装在创建事件。

### 4.3 写当前事件时只带相关历史

写作阶段由 Coordinator 和 FinalWriter 配合，机制叫 ReIO。输入侧：Coordinator 按当前子事件压缩先前历史，只保留相关事件和人物，摘要可缓存。输出侧：Coordinator 对照预期结构重写偏离的段落。论文观察到，输入大约超过 10,000 字符后，模型容易丢早期情节。滑动窗口实验里，对 15,000 token 以下的文本，压缩中间历史、保留近端上下文的效果最好。

消融去掉输入压缩后，输入变长，整体质量下降。去掉输出重写后，相关性从 4.1 降到 3.7。两步都有用，但职责不同：压缩决定写之前看见什么，重写决定写完后是否还贴着事件。

落到 StoryOS 时，写作子 Agent 在启用前先收到事件图主线：

- 主 Agent 读取事件图已确认的结果，组装成不超过 4000 字的主线。里面是当前叶子事件、相邻事件、相关人物状态、已触发的承诺，以及检索到的短证据。
- 事件图没有已接受的结果，或用户还没生成事件图时，主 Agent 把选择交给用户。用户确认先生成事件图，就委派 `event-graph`，完成并接受后再回到写作交接。用户选择继续写作，写作子 Agent 才在没有主线的情况下启用，并且提示里标明主线已被放弃。
- 写作子 Agent 按主线写正文。`ChapterGenerationService` 内部仍是单轮、无工具，指令已经带上主线或放弃标记。
- 输出检查对照当前叶子，报告遗漏、合并、擅自新增和提前写出的后续事件。检查结果不自动覆盖正文。
- 历史压缩的缓存如果要做，缓存键必须包含大纲 revision 和所依据的章节修订。大纲或正文变了，旧摘要失效。首版可以每次现算，不必先做缓存表。

论文用 AutoGen 把上述职责做成对话式智能体，并用 LONGSTORY 微调小模型。StoryOS 不复现这套训练，也不在引擎里新写编排器。主 Agent 是书籍对话，子 Agent 由产品运行时 Skill 编译。事件图子 Agent 负责主线；写作子 Agent 只在主 Agent 取到这份主线之后启用。模型输出仍是结构化候选或正文预览，经确认后提交。Agent、Skill 和工具的清单见后端架构。

## 5. 写作控制：DOC

DOC 说明一件 STORYWRITER 没有展开的事：大纲越细，正文越容易漏掉低层事件。它用详细大纲生成器把短大纲递归扩成树，再用详细控制器迫使段落贴住当前叶子。

可直接采用的生成规则：

- 叶子才是写作单位。每个叶子是一件具体的事，并带有场景和角色。父节点提供祖先约束，不单独生成一大段散文。
- 起草当前叶子时，提示里可以放入下一个叶子的概要，用来改善过渡。DOC 明确观察到，若缺少对当前叶子的约束，模型会提前把未来事件写出来。所以未来上下文只给紧邻的下一项，并且指令写明不得展开该项。
- 控制强度过低会跑题，过高会重复并损失创造性。DOC 的控制器从 0 逐步加大，叶子完成后重置。StoryOS 没有逐 token 控制器，对应做法是：指令里当前事件的约束写全，全书弧和后续事件只留短要点；生成后用覆盖检查看这一叶子是否真正出现。
- 叶子细节会不一致，有的过虚，有的过细。展开节点时限制一次只展开一层，并由用户确认后才继续。检测出的场景和角色可能不完整，因此地点和人物始终是可编辑字段，不把模型输出当成已确认事实。
- 大纲里的错误会在起草时级联。所以候选大纲先过确定性检查，再允许用来生成正文。

DOC 的详细控制器是在 OPT-350m 上按 FUDGE 训练的逐 token 判别器，实验规模大约是深度 3、每叶子最多 512 token 的短篇。这一实现不移植。StoryOS 用提示约束、上下文预算和生成后检查达到同一目标：当前叶子被写到，未来叶子不被提前兑现。

DOC 相对 Re3 的人工评估提升是情节连贯性 22.5 个点、大纲相关性 28.2 个点、趣味性 20.7 个点。消融表明，趣味性主要来自更细的大纲，控制器主要提升对低层叶子的忠实度，并可能略损趣味性。这支持 StoryOS 把细节放在规划节点上，同时把正文生成的约束限制在当前叶子，而不是把整棵树的每条约束都压进同一次生成。

## 6. 编辑层：GraphStory

GraphStory 把事件图放在作者和模型之间。作者编辑图，模型根据选定路径给出建议和正文，建议和原稿在界面上可区分。它解决的是构思和迭代，不是长篇自动写书。

可直接采用的交互规则：

- 两级粒度同时存在。宏观是块，微观是块内的事件列表。StoryOS 的树已经有故事弧、情节节点和场景事件，首版用树和时间线切换粒度。自由画布、自动布局和复杂边编辑器推迟。
- 生成分两段，且不改作者已有事件。第一段在选中块内部补充事件，改善局部连贯和篇幅。第二段沿选定的块序列补充过渡事件。新增事件以候选出现，作者逐项接受、编辑或拒绝。
- AI 事件和作者事件必须能溯源。GraphStory 用颜色区分，并把块映射到生成出的散文片段。StoryOS 用候选 patch 的操作来源，以及章节映射上的 `coverageStatus`：`planned`、`drafted`、`verified`、`deviated`。
- 故事、流程、版本三级组织用来并行探索方向。首版一本书只有一个当前大纲，`revision` 只做乐观并发。正式分支和版本树推迟到 `outline_variants`。
- 用户研究里的主要失败是一次塞入太多新事件，作者难以判断该留哪条。所以展开和过渡建议都要有数量上限，并在预览里按块分组，不能一次重写整棵树。

GraphStory 的实验对象是中短篇，参与者是写作专业学生，对照是 ChatGPT。它证明结构化中间层能降低组织叙事的负担，不证明无限画布适合桌面长篇工作区。关系在首版用列表和选择器编辑；图视图等关系类型稳定后再加。

## 7. 叙事承诺：CFPG

CFPG 处理另一类长程失败：正文局部连贯，但早期埋下的承诺没有在该兑现时兑现。它把每个承诺写成三元组。

- 伏笔 F：确立一笔因果债务的铺垫。
- 触发 T：使这笔债务变得可以行动的条件或先决事件。
- 兑现 P：了结该债务的收尾事件。

生成循环是选择、续写、更新。待决池里只有触发条件已被当前上下文满足的承诺，才进入这一步的提示。续写之后再判断哪些承诺已经落地，并抽取新铺下的承诺。论文用《巴斯克维尔的猎犬》的靴子说明：失踪是伏笔，追踪手段被揭示才是触发，在此之前解释靴子用途就是过早兑现。

对 StoryOS，承诺是独立实体 `NarrativePromise`，不是节点备注。状态为 `planned`、`seeded`、`eligible`、`paid_off`、`abandoned`，分别对应计划、已铺设、可兑现、已兑现、放弃。铺设、触发、兑现各关联一个可空节点。首版状态由用户维护；AI 可以建议迁移并写明理由，不能自行把承诺标成已兑现。

写作上下文只注入状态为 `eligible`、且触发节点已经映射到当前章或更早章节的承诺。其余承诺留在大纲里，不进入那条 4000 字指令。删除或移动关联节点时，预览必须列出受影响的承诺。

CFPG 归纳的六类错误可以直接当作检查项，而不实现它的自动编码函数：

| 错误 | 检查时看什么 |
|---|---|
| 过早兑现 | 触发节点尚未覆盖，正文却已经写出兑现要求 |
| 推迟后丢失 | 承诺长期停留在 `seeded`，后续章不再提及铺设内容 |
| 主题混淆 | 正文里的相似事件被当成目标兑现 |
| 状态未更新 | 节点已改，承诺仍指向旧节点 |
| 过度保守 | 触发节点已覆盖，承诺仍未被标为可兑现 |
| 间接关联失败 | 兑现以回溯方式出现，却没有连回铺设节点 |

论文的数据集构建、双验证器和叙事蕴含打分不进入产品。那些步骤用于从 BookSum 抽取句子级样本。StoryOS 的承诺由作者创建，证据锚到章节修订；目录重排不改变修订身份。

## 8. 其余材料只取判断

### 8.1 BiT-MCTS：先有高潮锚点

顺序从开头生成大纲，后段容易失去方向。BiT-MCTS 先抽出核心冲突和高潮事件，再向前规划后果、向后规划升级路径，并用全局整理修复缺口和节奏。弗雷塔格五段在这里是结构角色，不是搜索树的节点类型。

StoryOS 已有对应字段：大纲上的 `coreConflict`、`climaxSummary`，节点上的 `structuralRole`（开端、激励事件、上升、转折、危机、高潮、下降、结局、自定义）。新建大纲时可以提供“高潮优先”的候选路径。双向蒙特卡洛树搜索、奖励模型和主题语料库不实现。多候选加人工选择先代替搜索。

### 8.2 EVOSPARK：事件要留下状态变化

EVOSPARK 的主路径是角色社会模拟。三种控制范式里，层级化详细规划（HDP）是一棵严格事件树，顺序规划是里程碑之间允许即兴，自由涌现则去掉情节约束。实验显示，事件增多后，严格事件树对动态社会演化的增益小于更松的范式。这和 StoryOS 的产品位置一致：作者要情节保真，模拟社会不是首版目标。

可取的两条判断：

- 长篇记忆不能只追加旧状态。同一角色“既是朋友又是敌人”会同时残留。参与者记录 `stateBefore` 和 `stateAfter`，后一事件读取的是此前最近一次事件后状态，过期关系不跟全文日志一起注入。
- 角色、地点、情节必须对齐。不在场的角色不能执行当前事件。这是确定性检查：当前节点的地点和活跃参与者，要和前置节点的事件后状态接得上。临时提及的新角色停留在 `mentioned`，升级为正式角色留给以后的角色模块。

角色社会演化基座、场面调度智能体、创世/导演/架构师分工，都不进入 Agent 引擎。

### 8.3 成书论文：计划用短要点

《迈向人类水平的写书能力》把一本书收成由粗到细的规划脚手架：立意、章节、场景，再在训练中反过来展开成人类书稿。对事件模型有用的是表示方式。场景需要叙事功能，例如动作、对话、说明、世界构建和节奏。章节要有结构作用，不能只是场景摘要的拼接。短要点比稠密散文更适合重组。

`OutlineNode.summary` 因此保持短要点，约束放在目标、冲突、结果和叙事功能字段。`narrativeFunction` 取动作、对话、说明、世界构建、关系、悬念、过渡或混合。论文的监督微调、注意力分析和稀疏自编码器不进入本项目。

### 8.4 Agentic RAG 综述

综述讨论的是检索智能体的路由器、步数和工具边界。它不提供叙事事件结构。和事件模型的接口只有一条：人物、事件、伏笔在作者确认后，可以成为 novel scope 的新检索源。检索命中不能反过来充当这些实体的权威数据。写作图若要使用它们，是在 `retrieve` 之后增加确定性扩展，权威内容仍来自书库。

## 9. 合成后的流水线

一次从灵感到正文的路径如下。每一步的产出都是可编辑资产或可失效的检查结果。

```text
书籍前提 / 作者笔记
        │
        ▼
主 Agent（书籍对话）
        │  delegate_task → event-graph
        ▼
事件图子 Agent
        │  候选 patch，作者接受后成为主线
        ▼
事件树
  故事弧 → 情节节点 → 叶子事件
  关系：因果 / 前置 / 揭示 / 伏笔 / 对照
  承诺：伏笔、触发条件、兑现要求、状态
        │  用户确认映射
        ▼
启用写作前：主动读取事件图结果
  ├─ 已有已确认叶子 → 写作子 Agent，指令含主线
  └─ 没有结果，或用户尚未生成事件图
        询问用户
        ├─ 先生成事件图 → 事件图子 Agent → 接受后再交接
        └─ 仍然写作 → 写作子 Agent，指令标明主线已放弃
        │
        ▼
覆盖与承诺检查
  叶子是否出现、是否提前写出下一叶子、承诺是否被过早兑现
        │
        └──────────────► 回到事件树或正文修订
```

批量 AI 结果走 `OutlinePatch`：在内存中模拟并完整校验，再以单个事务提交。`expectedRevision` 不匹配时返回冲突，不静默覆盖。删除预览列出受影响的子节点、关系、章节映射和承诺。

事件图的读写只属于 `event-graph` 子 Agent。写作子 Agent 只消费已经接受的主线，不改事件图。主 Agent 通过 `delegate_task` 调度它们，工具名以 `docs/architecture/narrative-event-backend.md` 第 9 节为准。

## 10. 上下文包

生成或检查某个叶子时，外层按这个顺序组装，并在超出指令预算时从列表尾部丢弃。丢弃时保留定位，不把截断的半段伪装成完整约束。

1. 硬约束：主题、核心冲突、结局意图、当前叶子的目标、冲突、结果、地点、时间和参与者。
2. 祖先路径：从故事弧到当前叶子的父节点，每级一条短要点。
3. 局部邻域：叙述顺序上的前一个叶子、直接因果前置，以及紧邻的下一个叶子概要。下一个叶子标注为过渡参考，不得展开。
4. 本章其他已映射叶子的标题和状态。
5. 参与者在当前叶子之前最近一次有效的事件后状态。
6. 已触发且未兑现的承诺：铺设摘要、兑现要求、关联节点。未触发的承诺不进入。
7. 检索证据：向量或章节搜索命中的短片段，带章节、修订和偏移。索引不存在、不可用或正在重建时，错误原样向上传递，不改写成空证据。

整本正文、整棵详细大纲和全部承诺都不进入默认包。DOC 的未来上下文规则决定第 3 项只有下一项；STORYWRITER 的 ReIO 决定第 5 项是相关状态而不是全文历史；CFPG 的资格选择决定第 6 项只含已触发承诺。

章节生成的分页事件仍由现有生成服务发出。事件模型不改写作流的协议。

## 11. 首版范围

首版要有的事件能力：

- 一本书一个当前大纲，节点可多层，叶子表示可写作的事件。
- 节点上有短摘要、结构角色、叙事功能、目标、冲突、结果、地点文本、时间文本、两种顺序和状态。
- 关系、章节映射、参与者状态、叙事承诺。
- AI 候选：从简介生成大纲、展开选中节点、检查大纲。全部经 diff 预览后提交。
- 写作某章时按第 10 节组装上下文，生成后能看叶子覆盖和过早兑现。

首版推迟的能力，以及推迟的原因：

| 推迟项 | 原因 |
|---|---|
| 自由图画布、自动布局、手动画边 | GraphStory 的收益来自可编辑中间层；树、时间线和关系列表已能表达同样的数据 |
| 多条正式剧情分支、节点版本树与合并 | 先验证单大纲是否改善写作；`revision` 先解决并发 |
| 逐 token 控制器、事件模型微调 | DOC 与 STORYWRITER 的训练部件服务于论文实验，桌面应用用提示、预算和检查 |
| MCTS、角色社会模拟、自动判定兑现 | 搜索和模拟会改写作者事件；承诺状态保持人工确认 |
| 从正文持续反写大纲 | 覆盖检查只报告偏差。自动重写会让目录、正文和事件循环覆盖 |
| 事件和承诺进入向量索引 | 等实体确认并有稳定修订后，再作为新的 source kind |

## 13. 风险

- 字段过多会把写作变成填表。界面默认展示标题、摘要、顺序和章节映射；目标、关系、承诺和两种时间顺序收在详情里。
- 大纲和目录若互相覆盖，移动章节会改写情节，或改标题会被当成改事件。映射表是两者唯一的关联。
- 一次展开太多 AI 事件会重现 GraphStory 用户研究里的混乱。候选按选中节点分组，并限制新增条数。
- 叶子过细会让正文僵化。这是 DOC 已经观察到的控制强度问题。作者可以让节点停留在情节层，只有准备写的节点才标成事件叶子。
- 承诺若由模型自动标成已兑现，会把主题相似写成事实。状态迁移保留为建议，直到用户确认。
