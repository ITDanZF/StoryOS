# 事件图 AI 主线生成与书籍工作区写作联动设计

> 设计稿 · 2026-10-16<br>
> 目标：让作者在事件图中用 AI 建立并确认长篇小说主线，再让这份主线指导书籍工作区的章节写作。本文描述产品行为；实施与验收状态以[执行步骤](./event-graph-v1-implementation.md)为准。<br>
> 第一版按阶段落地的步骤见 [事件图第一版执行步骤分析](./event-graph-v1-implementation.md)。

## 1. 产品决定

**事件图负责故事往哪里走，书籍工作区负责这一段故事怎样被写出来。**

- 事件图生成、组织和维护全书层面的前提、核心冲突、故事弧、关键转折、因果关系与章节事件。AI 给出结构化候选，作者确认后才成为当前主线。
- 书籍工作区消费当前章节的已确认主线。AI 可以据此生成或续写正文；作者在此修改场景、动作、对白、描写与节奏。
- 正文改变关键事件结果时，系统展示它对后续主线的影响，由作者决定改正文、改主线或保留有意偏离。普通文字细节不要求回写事件图。

本期的成功标准是一条完整路径：**作者输入故事构思 → 接受一份可理解的宏观主线 → 把其中的叶子事件分配给一章 → 在书籍工作区看到本章主线并据此写作 → 能辨认本章哪些计划事件已写到。**

“主线”在这里是有因果与状态变化的叙事计划，不是 AI 一次生成的整本正文，也不是章节标题列表。全书可以先有少量关键锚点；临近写作的部分才展开到可写的叶子事件。

## 2. 当前实现边界

事件图页面已读取当前书籍快照，并在同一画布中展示可拖动事件、底部阶段范围与右侧 Markdown 文档；静态 JSON 示例有独立入口。AI 候选、章节映射、写作交接和写后核对已有代码入口，完整桌面端场景仍需按[执行步骤](./event-graph-v1-implementation.md)验收。Markdown 自由段落及关系的原子保存尚未打通；静态示例不代表当前书籍数据。

沿用 [`narrative-event-model.md`](./narrative-event-model.md) 和 [`narrative-event-backend.md`](./narrative-event-backend.md) 的边界：事件图的业务数据属于 story 层，目录负责稿件位置，章节正文拥有自己的修订；`src/main/agent` 不承载书籍业务。现有接口一次只给一份候选 patch，本期按此设计，不引入多套正式主线或版本树。

## 3. 作者看到的三个层级

| 层级 | 需要回答的问题 | 最少展示的信息 | 作者可做的事 |
|---|---|---|---|
| **全书主线** | 主角追求什么？核心冲突如何升级？哪些转折改变方向？高潮和结局意图是什么？ | 前提、主题、核心冲突、关键锚点、各弧的目标与结局方向。 | 生成候选、改写、接受、调整关键事件。 |
| **故事弧与章节安排** | 主线如何分段推进？支线何时交汇？每章应造成什么变化？ | 弧内关键事件、前后因果、叙述顺序、章节映射、尚未分配的叶子。 | 展开一层、调整关系和顺序、把叶子映射到章节。 |
| **本章主线** | 写这一章时必须完成什么，哪些细节可以自由创作？ | 已确认叶子的目标、冲突、结果；人物入场状态；前置事件；可兑现承诺；下一叶子的过渡边界。 | 选择本次写作范围，进入书籍工作区手写、续写或生成。 |

事件节点应表达一次**行动或遭遇 → 阻力 → 可观察结果**。作者随手记下的想法可以保持草稿；进入写作交接的叶子必须是已确认、已映射到当前章的事件。结构角色、人物变化与伏笔在需要时展开显示，不把全书规划变成逐格填表。

## 4. 主流程

```mermaid
flowchart LR
  A[作者提供构思和全书设定] --> B[AI 提议一层主线候选]
  B --> C[作者审阅差异并接受]
  C --> D[局部展开并映射章节]
  D --> E[预览本章主线]
  E --> F[书籍工作区写作和细节修改]
  F --> G[核对关键事件与正文]
  G -->|关键结果改变| C
  G -->|主线仍成立| D
```

### 4.1 建立全书骨架

无事件图时，页面明确展示空状态，作者先建立全书设定，至少给出标题和一段构思；主题、高潮和结局可以暂时未知。随后选择“顺序规划”或“高潮优先”，点击**生成主线**。生成范围默认是全书下一层：一次最多给出 8 个关键节点，重点是开端、转折、高潮或收束之间的因果推进，不提前填满所有章节。

当前 `proposeOutline` 能在无快照时返回候选，但 `applyOutlinePatch` 需要已存在的大纲。首期推荐**先明确创建空大纲，再生成候选**：空大纲本身是作者已建立的项目资产；放弃候选只清除候选，不删除空大纲。这样界面状态与现有 API 一致，避免“取消 AI 结果却留下了用户不知道的大纲”。

已有大纲时，作者选择全书、某阶段或某节点作为范围，再生成下一层或补充关键连接。`instruction` 保留作者的具体要求。每次生成只影响选定范围；对未点名的既有节点不改原文。候选返回 `repairable` 时展示问题并允许修改要求后重试，不把无效内容放到正式画布。

### 4.2 审阅和确认 AI 候选

候选在图中使用独立状态，并在侧面板列出：新增节点、被修改节点、新关系/承诺、预计影响的章节，以及每项的目标、冲突和结果。作者能先看懂“故事如何因此改变”，再决定是否接受。第一期支持**整份候选接受、拒绝、重新生成及接受前编辑候选内容**；逐项勾选需要重建并校验操作依赖，可在真实使用显示需求后增加。

提交带候选的基线 `expectedRevision`。修订已变化时保留候选，展示冲突并要求重新预览；不得静默覆盖。作者确认前，候选不参与章节写作交接。图上“输入一个想法”仍是捕获草稿入口，与调用模型的“生成主线”明确区分。

### 4.3 从主线到章节

作者按需展开近期准备写的部分，将足以指导写作的叶子事件映射到章节；关键事件本身也可以是叶子，不必逐个补子节点。同一章可有多个叶子；一个叶子只属于一个章节，跨章事件可拆为父节点与多个子事件。章节筛选时，右侧显示“本章要完成的变化”，不在事件图编辑正文。移动事件的讲述顺序、改变阶段归属或删除节点时，应说明对章节映射、因果关系和承诺的影响。

书籍工作区打开某章时，显示轻量的**本章主线**入口：事件清单、已确认状态、当前覆盖状态和“查看写作指导”。入口来自已存快照及章节映射，不维护第二份大纲。

### 4.4 写作前交接

作者从事件图的章节筛选状态或书籍工作区的“本章主线”入口打开同一份交接预览。预览说明：

1. 本次选中的已确认叶子，以及各自的目标、冲突、结果。
2. 直接因果前提、人物此前状态和本章可兑现承诺。
3. 紧邻的下一叶子，只用于过渡，不在本章展开。
4. 当前大纲 revision，以及将送入写作器的最终指令和字数预算。

这些信息由 `loadEventGraphHandoff` / `OutlineContextBuilder` 从正式快照组装；交接是当前修订的**派生结果**，不另外维护可漂移的“章节主线副本”。作者修改选中叶子或大纲后，交接需重新计算。`too-large` 时显示超预算原因，引导减少本次叶子；缺少主线时明确提供“先生成事件图”与“仍然写作”。继续写作须沿用现有放弃主线标记，不能让正文看起来像受事件图指导。

作者确认后进入**书籍工作区**执行章节生成、续写或手写。事件图负责交接，生成正文的进度、失败重试、修订保存与文字编辑由书籍工作区承接。这样作者写完可直接修改细节，不需要返回图上找一段刚生成的正文。

### 4.5 写后核对

生成并保存章节修订后，已选叶子进入待核验状态；“已覆盖”必须经作者确认。正文页显示每个计划事件的状态，并支持跳到证据片段。`reviewChapterCoverage` 的 AI 结果是建议，应附节点和正文证据；章节或大纲修订变化使旧结论过期。

只有正文改变**关键事件结果、人物状态、因果前提或承诺兑现**时，才提示回到事件图评估后续影响。作者可选择改正文、预览并接受新的主线 patch，或保留有意偏离。对白、描写和局部场景的修改留在书籍工作区。

## 5. 两个界面的主要信息和操作

### 5.1 事件图

- 顶部是可折叠的全书设定：前提、主题、核心冲突、高潮和结局意图。空字段显示“待定”，不由 AI 默默补成事实。
- 主区始终是一张可拖动的画布，事件总体从左到右推进；阶段用底部大括号标示范围。卡片保留标题与一句变化，选中事件才强调直接语义关系；右侧 Markdown 文档承载目标、阻力、结果、人物与写作边界。章节筛选只改变当前关注范围，不创建另一张图。
- 首要操作是“生成主线”“展开选中范围”“预览候选”“为章节安排事件”。选中章节后提供“查看本章主线 / 前往书籍工作区”。
- 右侧文档解释当前选择的**目标、阻力、结果、因果前提与后续影响**；点击文档内的节点链接可在原画布定位。全书和章节没有选中节点时，展示摘要与下一步。
- AI 候选、已确认节点、草稿、写作中、覆盖和需修订状态可辨认；检查结果区分结构错误与建议。长篇规模下按范围聚焦，避免全书常驻所有边。

### 5.2 书籍工作区

- 当前章节旁提供可收起的“本章主线”参照，列出已确认叶子与本次写作范围；点击可回到事件图的对应节点。
- 启动 AI 章节写作前展示最终交接预览，包括“本章必须完成”和“下一事件只作过渡”。作者在此选择续写或重写；手写正文也能阅读同一份主线。
- 正文编辑保持现有工作区的文本体验。只在作者要求核对时展示事件覆盖建议和证据，不让图的所有字段占据写作空间。
- 检查出重要偏离时给出影响范围和返回事件图的入口，保留当前正文修订；不直接修改主线。

## 6. 状态、异常与真实数据原则

| 情况 | 界面行为 |
|---|---|
| 当前书无大纲 | 显示建立全书设定的空状态；不展示示例故事。开发演示使用独立入口和显著标记。 |
| AI 正在生成 / 返回无效候选 | 显示范围、进度或可修复问题；正式图不变，可重试。 |
| 候选与当前 revision 冲突 | 保留待审内容，重新读取快照并展示差异；作者重新决定。 |
| 叶子未确认或未映射 | 在章节交接中说明缺哪一项，给出到对应节点的路径。 |
| 无主线仍要写作 | 显示明确选择；沿用 `waived` 交接结果，不伪称有事件图指导。 |
| 主线超出写作预算 | 呈现 `too-large`，允许减少本次叶子；不截断硬约束后继续写。 |
| 生成或保存失败 | 正文和事件图保留各自最后成功的修订；显示可重试错误，不假报覆盖。 |
| 正文或大纲后来修改 | 旧覆盖判断标为过期，重新核对后才更新状态。 |

数据来源始终区分：**正式大纲快照、未提交 AI 候选、界面临时草稿、章节正文修订、检查建议**。页面不能在读取失败时静默显示 `sampleDocument()`，也不能用空字符串或默认字段掩盖必填数据缺失。

## 7. 分阶段落地

| 阶段 | 改动重点 | 可验收结果 |
|---|---|---|
| **A. 真实主线与 AI 候选** | 让事件图加载当前书籍快照和真实章节；明确空状态；接通全书设定、生成范围、候选预览、确认与修订冲突。 | 作者能从自己的构思生成并保存一份不超过 8 个关键节点的全书骨架，重开书籍后仍存在。 |
| **B. 章节映射与写作交接** | 把已确认叶子映射到章；在两处展示同一份本章主线预览；从书籍工作区触发手写参照或 AI 章节生成。 | 作者能依据选中事件写一章；写作器收到的是该章正式快照派生的指令。 |
| **C. 写后反馈** | 展示覆盖建议、正文证据与修订过期；重要偏离跳回事件图并预览主线改动。 | 作者能判断本章关键变化是否落实，并决定是否影响后续主线。 |

首期先完成 A 与 B 的纵向链路，再拓展 C。人物知识顺序的正式模型、完整版本树、多套并行主线和全书一次性自动写完可待真实长篇使用验证。单画布已经作为当前交互方向；关系与承诺能力先为交接提供约束，无需等待高级功能齐备才开始写作。

## 8. 验收场景与质量标准

1. **从零开始。** 新书打开事件图是空状态；作者输入构思、生成候选、编辑并接受。取消候选后正式节点不增加；重新打开仍能看见已接受主线。
2. **持续展开。** 作者选择一条故事弧生成下一层。AI 只提议该范围的一层，已有未点名节点不被改写；无效候选说明问题。
3. **写第一章。** 作者把两个已确认叶子映射到第 1 章，预览本章主线，进入书籍工作区生成或手写正文。正文中可随意调整对白与描写；下一叶子不被提前写出。
4. **处理偏离。** 作者把原定“主角发现证据”改成“同伴先发现证据”。系统显示人物知识与后续揭示可能受影响，作者选择保留正文并预览主线修改；原正文不因图上操作丢失。
5. **失败与过期。** AI 候选无效、修订冲突、交接超预算或正文保存失败时显示真实状态。正文再次修改后，先前“已核验”不能继续冒充当前结论。

衡量设计是否有效，应看作者能否回答“这章为什么存在、它改变了什么、如何引向下一章”，以及正文能否在保有创作自由的同时守住全书因果与承诺。节点数、生成字数和关系线数量不是质量指标。对单线、多支线和非线性悬疑作品分别验证；研究中层级规划与事件式协作有助于长程连贯和组织创意，但这些结果不能代替真实长篇作者的任务测试：[DOC](https://arxiv.org/abs/2212.10077)、[GraphStory](https://arxiv.org/abs/2606.16102)。
