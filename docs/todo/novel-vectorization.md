# 小说正文向量化

> 2026-09-22 · 宏观范围说明，不含实现  
> 主题只有一件事：把已经保存的小说正文做成向量，供以后的片段检索和相似度检索使用。

## 1. 要做的事

StoryOS 的小说正文已经落在每本书的 `book.sqlite` 里。当前章由 `chapters.current_revision_id` 指向一条不可变修订，正文纯文本在 `revision_documents.plain_text`。

这些文本今天只能按字面查找。`search_book_chapters` 对当前修订做子串匹配。设置里的 Text Embedding 只会向兼容接口发一次连通性测试，返回的向量不保存，也没有任何检索去读它。

因此还不能按意思找回一段已经写过的内容，也不能拿一段正文去找书里相近的段落。向量数据库这一步就是补上这层数据：以当前已保存正文为来源，生成可按书重建的向量。片段检索、相似度检索以及其他更复杂的检索，都建立在这同一套向量上，而不是各自再存一份正文。

## 2. 向量化的数据

索引对象是一本书里尚未删除的章节的**当前修订纯文本**。

一条向量对应正文中的一个片段，并带有能回到原文的身份：`book_id`、`chapter_id`、`revision_id`，以及片段在该修订纯文本中的位置。章节 ID 在导入复制后可能出现在另一本书里，所以必须带书籍。内容以该修订已有的 `text_hash` 和片段自身的哈希区分，同一修订不重复嵌入。

按书隔离。查询只使用当前这本书已发布的向量。

下列内容不进入这套小说向量：

- 未提交草稿。草稿仍只服务当前编辑，正式保存后再索引。
- 历史修订。默认表示“这本书现在写成了什么样”。
- 会话记录、检查点、技能、书架摘要、阅读器生成的扉页和目录。
- 项目目录里的文件。那些文件已有自己的全文索引，不是小说修订。

书名、简介、卷摘要是短文本，和正文片段不是同一类检索单位，这一步不放进正文向量。

## 3. 向量库的角色

向量是派生索引。小说事实仍以书库修订为准。检索结果若和当前修订不一致，以修订为准，这条命中作废。

向量库未建立、正在重建或损坏时，编辑、阅读、导入导出，以及现有的字面搜索保持可用。

正文变化通过已有的保存结果来跟踪。正式保存会移动 `current_revision_id`，并在 `book_changes` 里留下章节变化。索引在这之后更新对应章节。章节进入墓碑后，新的检索立即不再使用它。`source_generation` 变化表示整书换代，该书索引按新一代重做。

把文本变成向量可以继续用现有的 embedding 配置和 `TextEmbeddingGateway`。哪一本书、哪一版修订、向量文件放在哪里，属于 `src/main/story` 的书籍数据，不放进通用 Agent 引擎。对话模型配置和 embedding 配置已经分开：更换聊天模型不需要重算向量；更换 embedding 模型或维度，则整批向量按新的空间重新生成。

存储上，向量目录跟书走，放在受控的书籍目录中，可以整书删除后重建。不把向量列写进 `revision_documents`，也不把小说片段放进保存会话的 `project.sqlite`。

## 4. 这层数据以后怎么被检索使用

片段检索和相似度检索读的是同一套已发布向量，差别在查询输入：

| 后期能力 | 查询输入 | 返回 |
|---|---|---|
| 片段检索 | 一个问题，或一段要查找的描述 | 本书中相关的原文片段，以及章、修订和位置 |
| 相似度检索 | 一段已有正文 | 本书中与它相近的其他片段，以及章、修订和位置 |

返回的是有限片段和定位，调用方再按修订号回读原文。向量文本不写回章节表。

更后面的检索，例如跨章节对照、带关键词的混合召回、把检索片段放进 Agent 上下文，都复用这里的书籍范围、修订身份和已发布向量。那些策略另做，不改变这一步的数据主题。

专业资料库、人物和大纲不在这一步里。更大范围的设计仍见 `docs/architecture/database-vnext/02-vector-rag.md`。那份设计稿里的资料库和具体向量引擎尚未接入；本稿不提前展开它们。
