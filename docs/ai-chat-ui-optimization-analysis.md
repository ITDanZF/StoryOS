# StoryOS 右侧 AI 聊天区 UI 优化分析

> 状态：分析与推荐方案
> 范围：仅涉及右侧 AI 聊天区的 UI、视觉和交互呈现，不修改 Agent 底层协议、工具执行机制或业务能力。

## 1. 背景与目标

StoryOS 右侧 AI 聊天区已经具备用户消息、AI 文本、思考、工具调用、任务、错误和审批等独立节点，功能基础是完整的。当前问题不是“缺少聊天组件”，而是这些节点在视觉上没有组成自然、连续、易读的一次 AI 工作过程。

本次分析参考 `E:\workspace\deepseek-harness` 的聊天实现，目标不是逐像素复制，而是吸收它在以下方面的设计方法：

- 用户输入、思考、工具过程和最终回答具有明确层级；
- 流式状态持续但不抢眼，过程快速掠过，最终答案稳定留下；
- 工具调用默认是一行可读摘要，技术细节按需展开；
- 自动滚动尊重用户阅读意图；
- 大面积使用中性色，品牌色只承担选中、运行和主要操作；
- 输入区和正文共享稳定的宽度、间距与视觉轴线。

## 2. 参考实现的关键方法

deepseek-harness 的效果不是依赖某一个动画或颜色，而是由数据投影、节点渲染和视觉规范共同完成。

### 2.1 语义节点分别渲染

参考项目将助手正文、思考、工具调用、上下文注入、错误和用户消息分别交给专用组件渲染。例如：

- `AssistantNodeView.tsx`：助手正文；
- `ReasoningRow.tsx`：思考摘要和展开内容；
- `ToolRow.tsx`：工具状态、摘要和详情；
- `ContextInjectionRow.tsx`：上下文注入；
- `MessageItem.tsx`：用户消息和其他消息；
- `ChatNodeSeat.tsx`：根据节点类型分派视图。

这种结构的价值在于：过程信息可以很轻，最终回答可以很稳，错误可以只强调真正失败的部分，而不是让所有内容共享一种“消息卡片”样式。

### 2.2 统一的 16px 纵向节奏

参考项目在完整聊天视图中使用统一的 16px 流间距，同时在工具行内部使用 24px 单行高度。工具详情只有展开后才进入正文流。

这形成了两种节奏：

- 对话节点之间保持清楚的呼吸感；
- 思考和工具过程本身紧凑、快速、可扫读。

### 2.3 思考行只显示当前摘要

运行中的思考行显示最新一行，完成后回到第一行摘要。完整思考内容默认收起，用户需要时才展开。运行状态使用缓慢扫光，而不是不断新增高对比度动画元素。

### 2.4 工具调用采用“标题 · 摘要”结构

工具行默认只呈现：

```text
动作 · 对用户有意义的结果
```

例如：

```text
读取 · 第三章正文
搜索 · 找到 6 处相关设定
创作 · 已保存第四章正文
```

输入参数、输出、文件路径和技术错误放在展开区域。运行、成功、失败只改变图标、摘要颜色和轻量动画，不改变整体布局。

### 2.5 滚动由“用户是否仍在底部”驱动

参考项目不会因为任意组件尺寸变化就强制把用户拉回底部。只有用户仍然保持在底部时，流式新增内容才继续跟随。

“回到底部”按钮放在零高度悬浮槽位中：

- 不增加正文滚动高度；
- 不覆盖正文中心；
- 位于输入区上方；
- 输入框变高时仍保持正确距离。

## 3. StoryOS 当前实现评估

### 3.1 已经做对的部分

StoryOS 当前节点模型已经包含：

- `user-message`；
- `assistant-text`；
- `reasoning`；
- `tool-call`；
- `task`；
- `turn-error`。

每个节点也保留了 `runId`、状态和顺序信息。因此，本轮 UI 优化不需要重新设计后端事件协议。

现有思考节点已经实现：

- 运行时读取最新一行；
- 完成后读取第一行；
- 默认折叠完整内容；
- 运行时扫光；
- 减少动态效果模式支持。

审批区独立接管输入区的方向也是正确的，审批操作不应被重新塞回思考或工具详情中。

### 3.2 当前主要问题

#### 3.2.1 所有节点近似等权排列

`ConversationFlow` 当前把节点放在同一个 `gap-4` 列表中。用户消息、过程说明、工具调用和最终回答虽然组件不同，但没有形成一次 Turn 的视觉边界。

结果是长回答看起来像一整篇文档直接塞进侧栏，用户很难快速区分：

- AI 正在解释；
- AI 正在执行；
- AI 已经完成；
- 哪一段才是最终结论。

#### 3.2.2 正文字号偏小

紧凑模式当前约为 `12px / 21px`。对于约 440–560px 宽的中文阅读区域，这个字号过小，长列表会显得密集。

推荐调整为：

| 内容类型 | 推荐字号/行高 |
| --- | --- |
| 最终回答 | 14px / 24px |
| 普通过渡说明 | 13px / 22px |
| 思考与工具行 | 12px / 20px |
| 次要状态与时间 | 11px / 18px |
| Markdown 小标题 | 15–16px / 24px |
| 输入正文 | 13–14px / 22px |

deepseek-harness 的完整聊天正文使用更大的 16px / 28px，但 StoryOS 是窄侧栏，不宜直接照搬。

#### 3.2.3 工具摘要泄漏内部实现

当前展示会出现：

```text
创作 · Edit saved chapter text: chapter_xxx
读取 · Execute read_book_chapter
```

问题包括：

- 中英文混杂；
- 暴露内部工具名；
- 暴露章节 ID；
- 用户无法从摘要快速理解结果；
- 工具成功后的视觉噪声仍然很强。

主界面应只显示业务语义。原始工具名、参数和 ID 只能出现在展开详情或调试界面。

#### 3.2.4 顶部上下文与输入区重复

顶部已经展示项目、书籍和章节标签，输入框内部又重复展示“项目 / 书籍 / 章节”路径。重复信息占用垂直空间，尤其在窄侧栏中影响明显。

建议保留顶部上下文栏，删除输入框中的完整路径。输入区最多保留一个短状态，例如“已引用第四章”。

#### 3.2.5 “回到底部”按钮遮挡正文

当前按钮居中悬浮，截图中已经覆盖最后几行列表。它既打断阅读，又强化了页面尾部的拥挤感。

建议改成右下角 32–34px 圆形图标按钮，放在输入框上方 12–16px，通过零高度悬浮槽位定位，不参与正文高度计算。

#### 3.2.6 Markdown 表现能力不足

当前 `MessageMarkdown` 是自定义的轻量解析器，只覆盖标题、一级列表、引用、分割线、代码块和少量行内语法。对于 AI 经常输出的嵌套列表、表格、任务列表和流式未闭合 Markdown，它会逐渐成为排版上限。

推荐后续替换为：

- `react-markdown`；
- `remark-gfm`；
- `rehype-sanitize`。

组件映射仍由 StoryOS 控制，因此不会失去现有视觉风格。

## 4. AI 图标专项分析

### 4.1 当前图标为什么显得突兀

当前图标由以下元素组合：

- 深黑到紫色的渐变背景；
- 白色通用 `Sparkles` 图标；
- 较重投影；
- 10px 圆角；
- 在纯白、浅灰、低对比度界面中占据高视觉权重。

它的问题不是单纯“图形不好看”，而是视觉语言与 StoryOS 主界面不一致：

1. StoryOS 主界面整体轻、平、克制，图标却像独立应用 Logo；
2. 渐变、投影和高对比底色同时出现，效果过重；
3. `Sparkles` 是通用 AI 符号，缺少写作产品识别度；
4. 紫色章节标签、发送按钮、运行动画已经承担品牌色，图标再次强强调会造成紫色堆积；
5. 图标与旁边的“新对话”标题争抢注意力。

### 4.2 最终方案：移除 AI 图标

实际界面验证表明，即使把渐变改成纯色并使用更简洁的自定义星形，图标仍然会产生明显的通用 AI 产品感，并继续与“新对话”标题争抢注意力。

最终决定不在聊天标题前显示任何 AI 图标：

- “新对话”直接作为标题起点；
- 在线状态继续由标题下方的绿色状态点表达；
- 运行状态由思考行、工具行和停止按钮承担；
- 不再通过头像、机器人、星光或魔法符号强调 AI 身份；
- 标题区回归 StoryOS 本身的轻量写作工具风格。

### 4.3 不推荐的图标方案

- 机器人头像：与小说写作场景距离较远，也容易显得工具化；
- 魔法棒：过于常见，容易产生模板化 AI 产品感；
- 羽毛笔加星星：信息量过多，小尺寸下容易糊成一团；
- 多色渐变 Logo：会继续放大当前视觉冲突；
- 持续旋转或发光：会在长时间写作时干扰注意力。

### 4.4 状态表达建议

在线、运行、审批和错误状态全部由现有语义组件表达，不再让标题图标承担状态职责。

## 5. 推荐目标结构

```text
BookAssistantPanel
├─ AssistantHeader
│  ├─ ConversationSwitcher
│  └─ HeaderActions
├─ ContextBar
├─ ConversationViewport
│  └─ ConversationFlow
│     └─ TurnGroup
│        ├─ UserMessage
│        ├─ ProcessStream
│        │  ├─ ReasoningRow
│        │  ├─ ToolCallRow
│        │  └─ TaskRow
│        └─ AssistantAnswer
├─ ApprovalComposer
└─ MessageComposer
```

### 5.1 `TurnGroup`

利用现有 `runId` 对节点分组，负责：

- 一次对话的上下边界；
- 过程和最终回答之间的间距；
- 运行、完成和失败状态；
- 最终回答的复制、重试等弱操作。

### 5.2 `ProcessStream`

统一承载思考、工具和任务节点：

- 同组过程间距为 4–6px；
- 单行高度为 24–28px；
- 完成后自动弱化；
- 运行时使用扫光；
- 错误只强调状态点和摘要；
- 展开详情使用独立浅色容器。

## 6. 视觉规范建议

### 6.1 颜色

| 用途 | 推荐值 |
| --- | --- |
| 面板背景 | `#FBFBFA` |
| 正文背景 | `#FFFFFF` 或透明 |
| 主文字 | `#262626` |
| 次级文字 | `#737373` |
| 弱文字 | `#A3A3A3` |
| 分割线 | `#EAEAEA` |
| Hover | `#F5F5F4` |
| 品牌紫 | `#6D4AFF` 或现有品牌紫统一值 |
| 品牌浅底 | `#F3F0FF` |
| 错误 | 仅状态和错误摘要使用红色 |

聊天正文当前的大面积紫色径向渐变应移除，或者降低到肉眼几乎不可察觉。品牌色只用于当前上下文、发送按钮和运行状态。

### 6.2 圆角

- 用户消息：18–22px；
- 输入框：16–18px；
- 工具详情：10–12px；
- 小按钮：8px；
- 标签：999px 胶囊圆角。

不建议所有组件都使用大圆角卡片，否则会产生过多“容器套容器”。

### 6.3 阴影

- 输入框仅保留一层很轻的悬浮阴影；
- 工具详情使用边框而不是阴影；
- “回到底部”按钮使用轻量二级阴影。

## 7. 交互规则

### 7.1 流式输出

1. 用户发送后，用户消息立即稳定显示；
2. 思考行出现并显示最新摘要；
3. 工具调用按发生顺序插入过程流；
4. AI 可以在工具前、工具间和工具后输出文字；
5. 过程节点完成后回归灰色；
6. 最终回答保持最高可读性；
7. 用户向上滚动后停止自动跟随；
8. 用户回到底部后重新接管自动跟随。

### 7.2 工具详情

- 默认收起；
- 点击整行展开；
- 展开不改变标题行高度；
- 输入和输出分别限制最大高度；
- 内部滚动不带动聊天主滚动；
- 成功摘要必须是业务语言；
- 失败摘要保留第一行错误，其余内容进入详情。

### 7.3 最终回答操作

完成后的最终回答底部可提供：

- 复制；
- 重新生成；
- 停止状态标记；
- 必要时的反馈入口。

操作按钮默认弱化或在悬停时显示，避免每段回答都出现一排高对比按钮。

## 8. 建议实施顺序

### 阶段一：高收益、低风险视觉优化

1. AI 正文调整为 14px / 24px；
2. 工具过程保持 12px / 20px；
3. 工具摘要移除英文、内部工具名和 ID；
4. 删除输入框内重复上下文路径；
5. 顶部上下文栏压缩到约 40px；
6. “回到底部”改为右下角圆形图标按钮；
7. 弱化或移除正文背景紫色渐变；
8. 移除标题前的 AI 图标。

### 阶段二：过程流编排

1. 新增 `TurnGroup`；
2. 按 `runId` 分组；
3. 新增 `ProcessStream`；
4. 统一思考、工具和任务的行高、状态与展开行为；
5. 区分中间说明和最终回答；
6. 增加最终回答的弱操作栏。

### 阶段三：Markdown 和滚动完善

1. 替换自制 Markdown 解析器；
2. 支持 GFM、嵌套列表和表格；
3. 处理流式未闭合 Markdown；
4. 精确记录用户滚动意图；
5. 让回到底部按钮跟随输入框高度；
6. 补充减少动态效果和键盘操作测试。

## 10. 验收标准

### 视觉验收

- 最终回答明显高于工具过程的视觉权重；
- 长篇中文回答不再显得拥挤；
- 默认界面不出现英文工具名和内部 ID；
- 标题区不再出现通用 AI 图标；
- 品牌紫只出现在必要位置；
- 顶部、正文和输入区不存在重复上下文信息；
- 回到底部按钮不遮挡任何正文。

### 交互验收

- 思考和工具过程可以交替出现；
- 工具前后可以正常插入 AI 文字；
- 思考和工具完成后默认收起；
- 用户向上阅读时不会被强制拉回底部；
- 回到底部后恢复自动跟随；
- 输入框增高不会覆盖回到底部按钮；
- 审批区独立于思考和工具详情；
- 减少动态效果模式下没有持续扫光或呼吸动画。

## 11. 结论

StoryOS 当前不需要再次重构 Agent 底层。现有 conversation node 和 `runId` 已足以支持目标效果，真正需要升级的是聊天 UI 的编排层。

推荐优先完成四件事：

1. 建立正文、过程和最终结论的视觉层级；
2. 把工具摘要转换为用户能理解的业务语言；
3. 修正输入区重复信息和回到底部按钮遮挡；
4. 移除标题前的通用 AI 图标，让状态反馈回到对应语义组件。

完成这些以后，右侧聊天区会从“功能都存在但信息堆叠”转变为“过程清晰、结果稳定、适合长时间写作”的 AI 工作区。
