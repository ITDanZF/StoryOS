# StoryOS V1 全量测试与发布验收计划

> 文档状态：待执行
> 目标版本：StoryOS V1
> 主要发布平台：Windows x64
> 测试目标：覆盖现有功能、关键异常路径与完整业务闭环，并以明确的发布门禁判断 V1 是否允许发布。

## 1. 测试目标

本轮测试不是只验证应用能否启动，而是需要确认以下结果：

1. 项目、书籍、卷、章节、正文和会话可以完成从创建到持久化恢复的完整闭环。
2. AI 对话、工具审批、正文生成和正文编辑能够在真实模型下完成一次完整闭环。
3. Agent 的 direct、planned、多任务、审查、取消、超时、失败和预算限制行为符合设计。
4. 项目之间的数据、文件、会话、运行记录和工具权限保持隔离。
5. 异常退出、模型失败、并发修改和用户拒绝不会破坏已有数据。
6. 安装包可以在干净的 Windows 环境安装、首次启动、升级启动和卸载。
7. 所有 P0/P1 缺陷关闭，自动化质量门禁全部通过，最终产物可被标记为 V1。

## 2. 发布范围

### 2.1 V1 范围内

- Electron 桌面应用启动、关闭和窗口行为。
- 模型配置与连接状态。
- 全局对话和项目对话。
- 项目创建、打开、切换、重命名、移除和删除。
- 书籍资料、卷、章节和正文管理。
- 富文本编辑、分页、查找替换、快捷键和保存。
- AI 对话、章节上下文、流式输出和会话恢复。
- AI 章节续写、重写、选区修改、全文修改和格式调整。
- 工具调用、审批、拒绝、取消和失败呈现。
- Agent 规划、调度、子任务、审查、重试、预算和结果汇总。
- SQLite 持久化、修订保护、项目隔离和异常恢复。
- Windows x64 打包、安装、运行和卸载。

### 2.2 V1 暂不要求

- 多模型自动故障切换。
- 不同 Agent 使用不同模型。
- 分布式任务队列。
- 动态 Agent 市场。
- 应用重启后继续执行未完成的 Agent 任务。
- DOCX、EPUB、PDF 等当前尚未提供的导出功能。
- macOS 和 Linux 的正式发布验收；配置可以保留，但不阻塞 Windows V1。

## 3. 测试原则

- 每个用例必须记录实际结果，不以“代码看起来正确”代替执行结果。
- 自动化测试使用隔离的临时目录和测试数据库，不得污染用户真实数据。
- 真实模型测试使用独立测试项目、受限额度 API Key 和无敏感信息的测试正文。
- 涉及删除、覆盖和 AI 写入的测试，必须先准备可恢复的测试数据。
- 修复缺陷后至少回归缺陷所属模块、关联业务闭环和全量自动化测试。
- 测试期间不得为了通过用例而放松路径隔离、审批或并发修订保护。

## 4. 测试结果定义

| 状态 | 含义 |
| --- | --- |
| PASS | 实际结果与预期完全一致 |
| FAIL | 功能错误、数据错误、崩溃或结果与预期不一致 |
| BLOCKED | 因环境、账号或上游缺陷无法执行 |
| SKIPPED | 经确认不属于本次 V1 范围 |

缺陷等级：

| 等级 | 定义 | 发布要求 |
| --- | --- | --- |
| P0 | 数据丢失、越权访问、无法启动、无法安装、核心闭环完全不可用 | 必须为 0 |
| P1 | 主要功能不可用、频繁崩溃、AI 错写正文、恢复失败 | 必须为 0 |
| P2 | 有替代路径的功能错误、明显 UI/性能问题 | 原则上关闭；遗留必须书面确认 |
| P3 | 轻微文案、样式或低频体验问题 | 可记录到后续版本 |

## 6. 执行阶段

### 阶段 A：基线与静态质量门禁

1. 确认 Git 工作区只包含本轮明确修改。
2. 安装锁文件依赖并重建原生模块。
3. 执行 TypeScript 类型检查。
4. 执行全量 ESLint。
5. 执行全量 Vitest。
6. 执行分页 E2E。
7. 执行 Electron production package。

建议命令：

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run test:pagination:e2e
npm run package
```

当前已知基线：此前全量测试共 217 项，其中 190 项通过、27 项失败；失败集中在 Agent 新旧契约迁移。正式执行前必须先更新这些测试，`npm run check` 必须恢复为全绿。

### 阶段 B：模块自动化测试

执行并核验以下测试域：

- 富文本序列化、旧正文转换、字符统计和非法内容拒绝。
- 分页模型、分页引擎、DOM 测量、分页缓存和页面命令。
- 项目、小说、会话、修订和运行记录 SQLite 存储。
- 工作区路径隔离、读后写保护和并发 revision 检查。
- 文本、文件、书籍和在线编辑器工具。
- 模型路由、会话存储、Agent Runtime 和 Agent Executor。
- Planner、Scheduler、Reviewer、Synthesizer 和 Orchestrator。
- 运行预算、取消、超时、checkpoint 回滚和生命周期清理。
- 会话事件组装、批处理、渲染和审批组件。

### 阶段 C：桌面端人工功能测试

按第 7 节逐项执行。

### 阶段 D：完整业务闭环测试

按第 8 节执行从安装到重启恢复的用户场景。

### 阶段 E：安装、兼容性与发布产物测试

按第 9 节生成并验证安装包。

### 阶段 F：缺陷回归与发布评审

1. 修复所有 P0/P1。
2. 对每个修复执行定向回归。
3. 再次执行全量自动化和核心闭环。
4. 冻结候选版本并生成最终安装包。
5. 按第 11 节作出 Go/No-Go 决策。

## 8. 完整业务闭环验收

以下闭环必须全部通过，单个步骤通过不能替代完整场景。

### FLOW-01：新用户首次创作闭环

1. 在干净 Windows 用户环境安装 StoryOS。
2. 首次启动并配置一个有效模型。
3. 创建项目 `长夜测试工程`。
4. 创建书籍，填写书名、简介和状态。
5. 创建两个卷，并在第一卷创建三个章节。
6. 打开第一章，输入并格式化一段正文。
7. 保存后切换章节，再返回确认内容存在。
8. 在项目会话中询问当前书籍结构。
9. 在章节上下文中让 AI 分析当前段落。
10. 关闭并重启应用。
11. 确认项目、书籍、卷章、正文、会话和 AI 回复全部恢复。

验收：全流程无白屏、崩溃、数据丢失或跨项目串数据。

### FLOW-02：AI 续写与人工编辑闭环

1. 打开已有章节并记录当前 revision 和正文。
2. 请求 AI 续写章节。
3. 观察聊天任务节点与编辑器实时预览。
4. 如出现写入审批，确认审批摘要与目标章节正确。
5. 批准修改并等待生成完成。
6. 确认只产生一次最终 revision，正文没有重复增量。
7. 人工修改生成内容并保存。
8. 切换章节、重启应用并再次检查。

验收：AI 写入、人工二次编辑、保存与恢复全部成功。

### FLOW-03：AI 改写拒绝与冲突保护闭环

1. 选择一段正文并请求改写。
2. 在审批界面核对目标和预览后拒绝。
3. 确认正文和 revision 未变化。
4. 再次请求改写，在 AI 运行期间人工修改正文。
5. 允许 AI 写入。
6. 确认陈旧写入被拒绝，人工修改仍在。
7. 重新基于新 revision 执行一次改写并成功保存。

验收：拒绝、并发冲突和重新执行都不会造成正文丢失。

### FLOW-04：项目隔离闭环

1. 在项目 A 创建带有唯一秘密标记的章节和文件。
2. 在项目 B 创建独立章节和会话。
3. 在项目 B 要求 AI 搜索项目 A 的标记或访问 A 的路径。
4. 使用路径穿越、绝对路径、兄弟目录和 Windows 路径变体重试。
5. 切回项目 A，确认原数据未被修改。

验收：项目 B 无法读取或写入项目 A，错误信息不泄漏敏感正文。

### FLOW-05：多 Agent 规划闭环

1. 提交一个需要文本分析、改写建议和最终审查的组合任务。
2. 确认系统进入 planned 路径。
3. 验证任务被匹配到具备对应能力的 Agent。
4. 验证任务状态、依赖、审查和重试在 UI 中可追踪。
5. 等待 Synthesizer 生成最终答案。
6. 检查运行记录可还原调用链。
7. 对同类任务执行一次中途取消，确认完整传播。

验收：成功路径结果可信，取消路径无残留运行和后续输出。

### FLOW-06：异常退出恢复闭环

1. 准备已保存书籍、章节和会话。
2. 启动一个长时间 AI 任务。
3. 在任务运行期间强制结束应用进程。
4. 重新启动应用。
5. 检查项目、正文和已完成消息仍存在。
6. 检查中断运行被标记为已中止，不显示为仍在运行。
7. 重新发送消息并保存正文。

验收：数据库可继续使用，没有重复事件、锁死或半写入正文。

### FLOW-07：离线编辑与网络恢复闭环

1. 断开网络后启动应用。
2. 打开已有项目并编辑、保存、切换章节。
3. 发送 AI 消息，确认得到可理解的网络错误。
4. 恢复网络并重新发送。
5. 确认对话成功且离线期间编辑的正文没有丢失。

验收：本地创作不依赖网络，模型失败不破坏本地数据。
